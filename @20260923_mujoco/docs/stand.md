# 站立与斜面 demo：`cpp_stand/` + `cpp_slope/`

模型怎么来见 [`model.md`](model.md)，任务 2 的平地/趴卧结果见 [`task2.md`](task2.md)。本文写这两个 demo 的控制律、站姿怎么来的、实测数字，以及踩过的坑；通用的 MuJoCo 坑（`geom_sameframe`、相机不会跟地面转）在 [`../../docs/learn/mujoco.md`](../../docs/learn/mujoco.md) §6.7/§6.8，这里只留指针。

两个 demo 共用一个头文件 `cpp_stand/src/control.h`；`cpp_slope/src/slope.cpp` 是 `stand.cpp` 的副本 + 倾斜改动（按约定不做公共头提取，逻辑解耦靠复制后改）。

| 可执行文件 | 干什么 | 关键参数 |
|---|---|---|
| `cpp_stand/build/stand` | 平地：搜一个合法站姿、PD 顶住，判「四足站稳」；三种起点可选 | `--kp` `--kd` `--gravity-comp` `--seconds` `--mode` `--start raw\|stance\|rest` `--ramp SEC` |
| `cpp_slope/build/slope` | 斜面：地面绕 y/x 轴转 `--pitch/--roll`（**重力不动**），判「有没有离地/翻倒」；三种起点同样可选（会把起点摆到斜面上） | 同上 + `--pitch` `--roll` |

两个可执行文件共用同一个内核 `cpp_stand/src/control.h`，所以三种起点（`raw` / `stance` / `rest`）两边都有；`slope` 多出来的只是“先把起点摆到斜面上”这一步。两边默认起点**不同**：`stand` 默认 `raw`（直接从模型原姿态开始，见「控制律与站姿」），`slope` 默认 `stance`（原姿态在斜坡上更容易摔，对照表见「实测」）。

## 怎么跑

```bash
cd ..                                                                          # 仓库根目录（有 pixi.toml）
pixi run cmake -S @20260923_mujoco/cpp_stand -B @20260923_mujoco/cpp_stand/build -G Ninja -DCMAKE_PREFIX_PATH="$CONDA_PREFIX"
pixi run cmake --build @20260923_mujoco/cpp_stand/build
pixi run @20260923_mujoco/cpp_stand/build/stand                                 # 默认：官方 Simulate 窗口，5 仿真秒（起点 = 原姿态）

pixi run @20260923_mujoco/cpp_stand/build/stand --mode sim --start stance        # 起点换成站姿（无起步过程）
pixi run @20260923_mujoco/cpp_stand/build/stand --mode sim --kp 300 --kd 6       # 增益扫（见下：会判"未站稳"）
```

## 控制律与站姿

控制就是最朴素的关节空间 PD，可选叠加 `qfrc_bias`（重力 + 科氏项）做前馈：

$$\tau = k_p\,(q_{\text{des}} - q) - k_d\,\dot q \;(+\; \texttt{qfrc\_bias})$$

### 为什么不能直接拿模型的默认位形当 `q_des`

导出模型的默认位形（`qpos0`）看上去正是"站着"：直立、四腿伸直、脚底刚好触地（trunk z=0.5786）。但它**当不了目标**，两条都实测过：

1. **膝越界**。`FL/RL_calf range=[-2.5, -0.85]`、`FR/RR_calf range=[0.85, 2.5]`，而默认位形所有关节都是 0 ⇒ 膝离最近合法边界还差 **0.85 rad**。一开场限位力就上来了，症状是"**与增益无关的崩溃**"：实测 kp 从 100 加到 1500、带不带 `--gravity-comp`，末态几乎逐位相同，而 `|ctrl|` 冲到 200+ N·m（峰值 237，执行器 `ctrlrange` 才 ±20）。
2. **质心在足后 0.18 m**。即使把膝掰进合法区间、腿尽量伸直，质心的水平投影也落在四足中心**后面 0.18 m** ⇒ 静态就不平衡，狗会自己往后倒/走掉（不是控制没调好，是位形本身不是平衡点）。

所以目标姿态必须**搜**：搜索不读 keyframe、也不改 XML，纯粹由几何与限位决定。

### 稳态姿态怎么搜（每个"旋钮"在调什么）

膝关节在合法区间内取 `{0.9, 1.1, 1.3}` rad 三档，大腿角按膝的 `0.1 … 1.0` 倍扫（步长 0.05，共 19 档），左右腿符号由各自限位区间的正负号决定（不靠猜）；每一档把**基座沿 z 平移到"最低那只足底球刚好贴地"**，再用一个评分挑最优：

| 旋钮 / 步骤 | 在调什么 | 本模型的结果 |
|---|---|---|
| 膝弯曲量 `bend` | 站姿的高低 / 腿的折叠程度（下限被限位卡在 0.85 rad，所以不可能"直腿"） | 1.10 rad |
| 大腿比例 `frac` | **把质心前后挪**——决定"站不站得住"的关键 | 0.55×膝 |
| 基座平移 | 只影响高度，不影响平衡（保证初始四足着地） | z = 0.498 |
| 评分 = 质心水平投影 ↔ 四足中心距离 | 越小越好：质心要落在四足中心上 | **0.001 m** |

**怎么验**：输出里 `初始化：搜到站姿——…` 会把这四项都打出来；紧跟着的 `站姿静态重力力矩：1.1 0.3 0.4 … N·m` 是"守住这个姿态需要多少静态力矩"，一旦接近或超过 ±20 的限幅，这个姿态注定守不住（穿模崩溃那次这个数就是几百）。之后再看 `起始/末态/末 1 s` 三行指标。

**怎么改**：想站得更高/更低就改膝候选（`{0.9, 1.1, 1.3}`）；想更省算力就减少扫描档数；换模型/换 URDF 时不用手写常数——搜索会按新限位重新跑一遍。左右腿镜像、限位方向都是查出来的，所以四条腿谁正谁负不需要人工维护。

### 起点（`--start`）与起步斜坡（`--ramp`）

搜出来的站姿是**目标**；**起点**另有三种选法（`--start`），两个 demo 的默认值不同：

| `--start` | 起点 | 默认斜坡 | 谁默认用它 |
|---|---|---|---|
| `raw` | 模型加载时的原姿态（`mj_resetData`，不读 keyframe、不摆姿态：直立直腿、脚底刚好触地） | 0.1 s | `stand` |
| `stance` | 直接把狗摆到搜出来的站姿上（没有起步过程） | – | `slope` |
| `rest` | 场景自带的 `rest` keyframe（趴卧） | 1.5 s | – |

`raw` / `rest` 的起步都用同一个 `control.h::RampFrom()`：把 `q_des` 在 `--ramp` 秒内沿 smoothstep 从"起点关节角"推到站姿（**控制律不变**，只是目标随时间动；时钟是 `d->time`，窗口里暂停就跟着停）。

`raw` 的斜坡**必须很短**，原因就是上面第 2 条：原姿态的质心在足后 0.18 m，狗从 t=0 起就在往后倒，腿得在它倒下去之前收进去（5 s 与 30 s 结论相同）：

| `--ramp` | 末 1 s 最大位移（判定用） | 判定 | 现象 |
|---|---|---|---|
| 0.05 / **0.1（默认）** / 0.15 / 0.2 s | 0.0112 / 0.0135 / 0.0194 / 0.0249 m | ✓ | 收腿后站住，30 s 也不漂（离起点总位移 8–9 mm） |
| 0.25 / 0.4 s | 0.0358 / 0.0644 m | ✗ | 站是站着（z=0.4928、4 足触地），但收腿后还在挪，超过 3 cm 阈值 |
| 0.8 / 1.0 / 2 / 5 s | — | ✗ | 往后倒（末态倾斜 48–179°、0 足触地） |

`slope` 默认仍用 `stance`：斜面上本来就在往下滑，再叠加"收腿"这一下更容易摔——实测 `slope --start raw --pitch 15` 直接翻倒，而默认 `stance` 在 15° 是 ✓；`--start raw` 在斜面上的可用范围只到 10°（见「实测·斜面」的对照表）。

## 从趴卧起身（`--start rest`）

`stand` 默认从**模型原姿态**开始（`--start raw`）；加 `--start rest` 就把起点换成场景自带的 `rest` keyframe（趴卧），让狗自己站起来。**没有换控制算法，也没有另开一个目录**：还是同一个 `stand::StanceController`，只是 `q_des` 不再一步到位——`control.h` 里的 `RampFrom()` 把它在 `--ramp` 秒内从「趴卧关节角」按 smoothstep 推到站姿，之后保持不变。smoothstep 两端速度为零，起步/到位都不猛拉；用的时钟是 `d->time`，所以在窗口里按暂停，起身也跟着停。

**为什么做成参数而不是新目录**：控制律、场景、指标、判定全都没变，变的只是**起点**，而起点本来就是场景里已有的一个 keyframe——这和 `--seconds`、`--mode` 是同一类东西；新目录会复制一份 400 行的程序，只差二十来行。反过来，`cpp_slope/` 之所以单独一个目录，是因为它换了**世界**（地面倾斜）与判定语义（不再追求站稳），那是另一类改动。

**斜面上怎么起**：`cpp_slope` 也支持 `--start rest`，多出来的一步是把趴卧姿态**刚体旋转**摆到斜面上——偏移（相对平面上一点的向量）与朝向一起转（`q_pos ← g_floor_pt + R·(q_pos − g_floor_pt)`、`q_quat ← R∘q_quat`），旋转量与地面倾斜同一个 `R`，所以相对几何与水平时完全一样。**不能拿“基座到平面的法向距离”去反推基座位置**：那样算出来是 `0.1449·cos(pitch)`（15° 时差 5 mm），会把狗往平面里压。实测起点法向高度在任意 pitch 下都是 0.1449 m。另外 `--start rest` 时 `slope` 的判定多一条“真的站起来了”（末段法向高度不低于站姿 3 cm）：趴卧时也是有四足触地的（膝收着、足底仍碰地），光看触地数分不出“没起来”。

```bash
pixi run @20260923_mujoco/cpp_stand/build/stand --mode view --start rest              # 窗口里看它起身
pixi run @20260923_mujoco/cpp_stand/build/stand --mode sim --start rest --seconds 5   # 只仿真 + 判定（退出码 0/2）
pixi run @20260923_mujoco/cpp_stand/build/stand --mode record --start rest --seconds 5 --out @20260923_mujoco/output/cpp/stand_up.mp4
```

实测（`--start rest --seconds 5`；起点就是 keyframe：基座 z=0.1449、竖直度 0.00°、**4 个足底球**触地——躯干/小腿也压在地上，但“四足触地”只认 4 个足底碰撞球）：

| 斜坡 `--ramp` | 末态 z（站姿 0.4983） | 竖直度 | 四足触地 | 末 1 s 最大位移（判定用） | 离趴卧起点总位移 | 判定 |
|---|---|---|---|---|---|---|
| 0.5 s | 0.4928 | 0.02° | 4 | 0.0047 m | 0.0350 m | ✓（退出码 0） |
| **1.5 s（默认）** | 0.4928 | 0.02° | 4 | 0.0022 m | 0.0732 m | ✓（退出码 0） |
| 3 s | 0.4926–0.4927 | 0.02° | 4 | 0.0001 m | 0.1338 m | ✓（退出码 0） |

读法：斜坡越长，狗起得越"从容"（末段残余漂移 0.0047 → 0.0001 m），但沿途蹭出去的总位移越大（3.5 → 13.4 cm）——慢推时腿是"碾着地面"把身体撑起来的。表中的「末 1 s 最大位移」是从**起身完成那一刻**的位置算的（起身中那几厘米是必然的，参考点为什么这么选见踩坑 7），离趴卧起点的总位移单独打印；判定仍是末段四足触地 + 高度到位 + 竖直 + 不漂，所以 `--start rest` 这条判定的含义是「**站起来了，而且站起来之后没乱跑**」。

斜面上起身（`cpp_slope --start rest --seconds 5 --ramp 1.5`；漂移列是**切向**的，即沿坡滑下去的量）：

| `--pitch` | 末态法向高度（站姿 0.4978） | 相对法向倾斜 | 四足触地 | 起身后切向漂移 | 离趴卧起点总位移 | 判定 |
|---|---|---|---|---|---|---|
| 0° | 0.4928 | 0.02° | 4 | 0.0022 m | 0.0732 m | ✓ |
| 5° | 0.4931 | 0.29° | 4 | 0.0286 m | 0.1064 m | ✓ |
| 10° | 0.4933 | 0.60° | 4 | 0.0565 m | 0.2609 m | ✓ |
| 15° | 0.4936 | 0.87° | 4 | 0.0951 m | 0.4096 m | ✓ |
| 20° | 0.0165 | 178.60° | 0 | 1.4127 m | 2.1806 m | ✗ 没站起来/翻倒 |
| 25° | 0.1969 | 123.00° | 0 | 1.0437 m | 2.2587 m | ✗ 没站起来/翻倒 |

读法：≤15° 能起身并站住（起身过程中沿坡下滑 3–41 cm，坡越陡滑越多）；≥20° 起不来（摔掉，退出码 2）。`--pitch 0` 那一行与 `stand --start rest`（同为 ramp 1.5）**逐位相同**（0.0022 / 0.0732）——两个程序共用同一个内核与同一份模型，只是场景多一张地面纹理，这正好互为校验。

两个使用注意：起点必须有 `rest` keyframe（传没 keyframe 的 `scenes/flat_scene_raw.xml` 会直接报错并退出，退出码 1）；`--seconds` 要大于 `--ramp + 1`（末段统计取最后 1 s），短了会打印一句提醒。

## 实测

### 平地：三种起点（`--mode sim`，默认 kp=200 kd=5）

| `--start` | 斜坡 | 起始基座 z | 末态基座 z（站姿 0.4983） | 竖直度 | 四足触地 | 末 1 s 最大位移 | 离起点总位移 | 判定 |
|---|---|---|---|---|---|---|---|---|
| **`raw`（默认）** | 0.1 s | 0.5786 | 0.4928 | 0.02° | 4 | 0.0135 m | 0.0087 m | ✓（5 s 与 30 s 都 ✓） |
| `stance` | – | 0.4983 | 0.4928 | 0.02° | 4 | 0.0045 m | – | ✓（5 s 与 30 s 都 ✓） |
| `rest` | 1.5 s | 0.1449 | 0.4928 | 0.02° | 4 | 0.0022 m | 0.0732 m | ✓（5 s） |

三种起点最后都落在同一个末态（z=0.4928、竖直度 0.02°、四足触地 4）——因为控制目标是同一个搜出来的站姿；区别只在起步过程与“末 1 s 位移”的量级（`raw` 起步后还有 1.3 cm 的余摆，`stance` 几乎没有）。

增益不是越大越好，**窄窗口**（同一判据，5 s，默认 `raw` 起点）：

| 参数 | 触地 | 水平位移（末 1 s） | 判定 |
|---|---|---|---|
| kp 150 kd 4 | 4 | 0.0076 m | ✓ |
| **kp 200 kd 5（默认）** | 4 | 0.0135 m | ✓ |
| kp 200 kd 5 `--gravity-comp` | 4 | 0.0137 m | ✓ |
| kp 300 kd 6 | 0 | 1.4089 m | ✗ 未站稳 |
| kp 500 kd 10 | 0 | 1.3578 m | ✗ 未站稳 |
| kp 50 kd 1 `--gravity-comp` | 4 | 0.0491 m | ✗ 未站稳 |

（增益窗口与起点无关：换成 `--start stance` 时结论一样，只是位移数字变成 0.0063 / 0.0045 / 0.0042 m。）

判定按「本 demo 不追求站在斜面上」放宽：**末段四足全程触地 且 机身法向朝上** 即通过；高度/倾斜/漂移只列出来供参考。

| 参数 | 落面后触地 | 末态触地 | 法向高度（站姿 0.4978） | 相对法向倾斜 | 切向漂移 | 判定 |
|---|---|---|---|---|---|---|
| pitch 0° | – | 4 | 0.4928 | 0.02° | 0.0045 m | ✓ |
| pitch 5° | 4 | 4 | 0.4931 | 0.29° | 0.0443 m | ✓ |
| pitch 10° | 4 | 4 | 0.4933 | 0.60° | 0.0926 m | ✓ |
| pitch 15° | 4 | 4 | 0.4936 | 0.87° | 0.1524 m | ✓ |
| pitch 20° | 4 | 1 | 0.0170 | 178.36° | 2.6633 m | ✗ 翻倒 |
| pitch 25° | 4 | 1 | 0.0302 | 165.75° | 3.0472 m | ✗ 翻倒 |
| pitch 30° | 4 | 0 | 0.1745 | 170.21° | 12.6842 m | ✗ 翻倒 |
| roll +10° | 4 | 4 | 0.4928 | 0.64° | 0.0928 m | ✓ |
| roll −10° | 4 | 4 | 0.4928 | 0.64° | 0.0928 m | ✓ |
| pitch 10° + roll 10° | 4 | 1 | 0.0163 | 178.27° | 2.5055 m | ✗ 翻倒 |

读法：这套「腿不动、只靠关节 PD 顶住」的站姿在 **≤15°** 能撑住（坡度越大越往下滑——15° 时 5 s 滑 0.15 m，属正常），**≥20° 就滑走并翻倒**（漂移 2.7–12.7 m）。想要更陡的坡得加步态/力矩分配，本 demo 不做。

换成 `--start raw`（默认 `--ramp` 0.1 s）作对照——斜面上一边收腿一边往下滑，裕度小很多：

| 参数 | 末态法向高度 | 相对法向倾斜 | 四足触地 | 切向漂移 | 判定 |
|---|---|---|---|---|---|
| pitch 0° | 0.4928 | 0.02° | 4 | 0.0135 m | ✓ |
| pitch 5° | 0.4931 | 0.29° | 4 | 0.0609 m | ✓ |
| pitch 10° | 0.4933 | 0.60° | 4 | 0.1157 m | ✓ |
| pitch 15° | 0.0178 | 178.05° | 0 | 2.4733 m | ✗ 翻倒 |
| roll 10° | 0.4938 | 0.42° | 1 | 2.1370 m | ✗ 翻倒 |
| pitch 10° + roll 10° | 0.1731 | 89.03° | 0 | 4.2106 m | ✗ 翻倒 |

即：`raw` 只到 **10°**（而且 roll 10° 就翻），所以斜面 demo 的默认起点保持 `stance`；`--pitch 0` 一行与 `stand --start raw` **逐位相同**（0.0135 / 0.0087），两个程序互为校验。

## 踩坑

### 1. 导出模型的默认位形（`qpos0`）违反膝关节限位 → 「与增益无关的崩溃」

症状：拿 `qpos0` 当 `q_des` 时，一开场就被限位力踢出去，**换多大增益都一样**（kp 100→1500、带不带补偿，末态几乎逐位相同，而 `|ctrl|` 冲到 200+ N·m/限幅 ±20）。完整的限位数字与"为什么它同时也不平衡"见上面「控制律与站姿」：**调增益没用的时候，先查位形本身是否合法/是否平衡**。

### 2. 直腿站姿的质心落在足后 0.18 m → 狗自己走掉

即使把膝掰进合法区间、腿尽量伸直，质心水平投影也在四足中心**后面 0.18 m**，静态就不平衡。修法就是上面那条搜索目标（**质心↔四足中心距离**最小，搜到 0.001 m），具体旋钮与验收方式见「控制律与站姿·稳态姿态怎么搜」。这也是判定指标里"水平位移"的物理来源；它同时解释了 `--start raw` 为什么必须用短斜坡（不加控制就往后倒）。

### 3. 斜面「落面」只压住最低的一只脚

把地面转过去、沿新法向把最低脚落到平面上，只有**一只**脚真的接触（实测打印「落面后：四足触地 2」）。补法：沿法向以 0.5 mm 为步长轻压，直到四足都进接触（最多 40 步），之后再跑仿真；打印里的「落面后：四足触地 4」就是这一步的结果。

### 4. 地面其实一直没转（`geom_sameframe`）——本 demo 最贵的一个坑

`--pitch/--roll` 原本只写了 `m->geom_quat[floor]`：模型字段读回来是对的，`d->geom_xmat` 与碰撞面却**一点都不动**，于是整个 demo 变成"狗自己歪着站在水平地面上"，而高度/倾斜/漂移都按我们自己记的 `g_up` 在算——全都自说自话。症状就是"看着像没转"（用户就是这么发现它的）。原因与修法见 [`../../docs/learn/mujoco.md`](../../docs/learn/mujoco.md) §6.7：要同时把 `m->geom_sameframe[floor] = 0` 清掉（`mj_local2Global` 见 `sameframe` 为真就抄世界体位姿，不读 `geom_pos/quat`）。修完后 pitch 15° 的指标变化能看出旧结果是假的：**相对法向倾斜 15.02° → 0.87°、切向漂移 0.1096 → 0.1524 m**（旧的 15.02° 正是"狗自己歪了 15°、地面是平的"的指纹）。

现在 `slope.cpp` 自带**自检**：改完地面 + `mj_forward` 之后，拿 `d->geom_xmat` 的第三列（地面在世界系的**实际**法向）与自己的 `g_up` 对比，不一致就直接报错退出（退出码 1），并把两个法向都打出来。另外顺手修掉了 `mju_copy4(m->geom_quat + 3*floor_geom, ...)` 的步长笔误（`geom_quat` 是 4 个一组，`geom_pos` 才是 3 个一组；地面恰好是 geom 0 才一直没暴露）。

### 5. 相机不会跟着地面转；斜面默认场景为什么要加棋盘格

倾斜后的画面里，"竖直方向"仍必须是竖直的（重力方向不变），而自由相机本来就是**重力水平**的——实测 pitch 0° 与 15° 两次算出的相机 `pos/forward/up` 逐位相同，`up·世界z = cos 20°`（`mjvCamera` 里也没有 roll 字段）。所以别怀疑相机，要先确认地面真转了（坑 4）。给斜面 demo 换默认场景 `scenes/slope_scene.xml` 的理由只是**可读性**：它等于 `flat_scene.xml` + 一张 MuJoCo 自带的棋盘格纹理（`builtin="checker"`，不需要外部图片，地面仍是同一个 `type="plane"`，物理逐位不变），有了格子才能一眼看出"斜了多少、往哪斜"。想回到纯色地面就显式传 `scenes/flat_scene.xml`。详见 [`../../docs/learn/mujoco.md`](../../docs/learn/mujoco.md) §6.8。

### 6. `--mode view` 收尾那行 wall 时间会误导

`main` 里的计时从**进程启动**算起，含开窗、`mj_loadXML`、`sim.Load()` 交接与收尾（本机约 1.7 s），而实时率只该由物理线程报。所以 `view` 模式下：物理线程自己打「已到 X 仿真秒（wall Y s，Z 倍实时）」，`main` 那行明确写成"wall 是 main 的总耗时（含开窗、加载与收尾），实时率看上面物理线程自己报的那行"。实测关窗后物理线程报 `1.00 倍实时`，`main` 的总耗时比它多约 1.7 s。**同一类问题的另一半（那个 Z 当初算错过）见坑 9。**

### 7. 起身那几厘米的挪动会把判定顶掉

`水平位移` 原本是相对**原点**（`m->qpos0` 的 xy）算的——起点就是站姿时，它恰好等价于"从出发位置走了多远"；但 `--start rest` 时狗必须挪几厘米才能把身体撑起来（实测 3.5–13.4 cm），沿用同一条 3 cm 判定就会"明明站得好好的却判未站稳 ✗"。修法不是放宽阈值，而是把参考点改对：`g_ref_xy` 默认仍是原点（站姿路径的数字一点没变，仍是 0.0045 m），`--start rest` 时在斜坡跑完那一刻把它挪到当时的基座位置，同时末尾另打印「末态离趴卧起点共 X m」；阈值继续管"站起来之后漂不漂"。`cpp_slope` 同一条规则，只是参考点换成了三维的 `g_base0`（漂移只算切向分量，法向沉降不算漂）。

### 8. “四足触地”一度把躯干也算进去了

原来的实现是"机器人任意 geom ↔ 世界体地面"的接触都算一只脚（按 geom 去重），站姿起点时恰好对（只有 4 个足底球碰地），但 `--start rest` 时趴卧的躯干/小腿也压在地上，于是"没站起来"也会被数成 4–5 足触地。改成**只认 4 个足底碰撞球**（`g_feet`，在模型里按 `type=sphere && contype≠0` 现查）后：起点实测仍是四足（趴卧时足底确实碰地），而 `slope --start rest` 额外加的“高度到位”那条把“没起来”堵住了。站姿路径的全部数字逐位未变（`stand` 0.0045 m、`slope` pitch 0/15 与表里一致）。

### 9. 「实时率」不能拿节流那一套计时算；`measured_slowdown` 要写实测值

三处同一个毛病：**分子与分母不同源**。

* **实时率用了会重置的基准。** 物理线程本来就有一对 `wall0/sim0` 是给**节流**当基准的（"目标时间轴 = 起点 + 活动墙钟 × speed"），而它在**界面按暂停**、**"落后超 50 ms 重新对齐"**时会被重置。实时率最初就拿了这对：分子是**总仿真时间**（`d->time`）、分母是**上次重置之后的墙钟**（`wall_elapsed()`）——只要中间重置过一次，这个比值就没意义。实测（`slope --mode view --start rest --pitch -10`）打出 `仿真 22.694 s，wall 5.13 s，4.42 倍实时`，而真实情况是"跑一段 → 暂停 → 再跑 5.13 s"，全程就是 1.00x。修法：报告另用一套**永不重置**的累加量（`wall_begin` / `sim_begin` / `paused_total`），暂停时长单独扣掉，报 `Δ仿真 / 活动墙钟`；节流仍用原来那对。
* **`measured_slowdown` 写的是目标值。** 界面里那个 Real-time 百分比读它，官方语义是**实测的** `墙钟/仿真`，界面再拿 `100/它` 与下拉框目标值比对、偏差超 10% 告警（详见 [`../../docs/learn/runtime-timing.md`](../../docs/learn/runtime-timing.md)）。原来塞的是 `min(1, 下拉框/100)`（目标值），于是界面永远"已对齐"——机器跟不上、中途调速都不会告警。现在写实测值。
* **录像收尾掺进了单步耗时。** `--mode record` 的 `单步耗时/实时率` 原来在 `rec->Close()`（等 ffmpeg 写完 moov）**之后**才取时间，把收尾也算进平均单步；现在在仿真循环结束时就把计时按下（三个程序都改了）。

复核：`已到 2.000 仿真秒（wall 2.01 s，1.00 倍实时）`而外面量到的真实间隔 2.03 s（无负载 / 2 个忙循环 / 8 个忙循环三种情况都一致）；在界面里暂停时，报告的 `wall` 里不含暂停时长。

### 10. 录像的出帧判据不能写成“距上次出帧过了 1/fps 就出”

`record.h::Capture()` 原来是 `if (d->time - last_time_ > 1/fps) 出一帧`。看着像“按仿真时间出帧”，实际是“**至少**隔 1/fps 才出”，而物理步长 `dt = 0.002 s` 与 1/fps 一般不整除 ⇒ 每帧实际隔的是**整数个 dt**，帧率被 dt 量化，而 ffmpeg 仍按 `-r <fps>` 打时间戳：

| `--fps` | 1/fps | 实际间隔（换算） | 5 仿真秒出帧（实测） | MP4 时长 | 后果 |
|---|---|---|---|---|---|
| 50 | 20 ms | 11×dt = 22 ms | 236 帧 | 4.72 s | 视频比仿真**快 6%** |
| 120 | 8.33 ms | 5×dt = 10 ms | 500 帧 | 4.17 s | 快 20% |
| 60 | 16.67 ms | 9×dt = 18 ms | 278 帧 | 4.63 s | 快 8% |

也就是说 `--fps` 名义上管时间轴、实际被 dt 吃掉了：画面里狗的动作比仿真里快（两个 1080p 产物 `--fps 120` / `--fps 60` 就是这么录出来的）。修法是把出帧时刻钉在**严格网格** `k/fps` 上：每出一帧就 `next_time_ = frames_/fps_`（按帧数推、不累加，避免浮点漂移），帧数变成 `≈ 时长×fps` 多 1 帧（收尾那一步也采一帧）。代价是帧时刻要对齐到最近的物理步（最多晚一个 dt = 2 ms），帧与帧之间仍按 1/fps 均匀排布、不累积。修完实测：1 仿真秒 @50/120/333 fps → **51 / 121 / 334 帧**；5 仿真秒 @50 fps → 251 帧（5.02 s）、@120 fps → 601 帧（5.008 s）。Python 侧的 `VideoRecorder` 一直是网格写法（`self._next_t += 1/fps`，跟不上时重设基准），两边现在一致；`fps > 1/dt`（本模型 500 fps）时物理步不够用，只能丢掉来不及渲染的网格点，这条 Python 侧也一样，见 [`../../docs/learn/mujoco.md`](../../docs/learn/mujoco.md) §7.5。
